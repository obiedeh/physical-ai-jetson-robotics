# Decisions

- 2026-09-17 — Everything parked until the Ludo flagship delivers (operator). Evidence: focus rule.
- 2026-09-17 — Real-arm data collection starts on the Yahboom M3 Pro, the only arm with a verified recording path. A physical Synria arm bring-up opens only if the operator confirms the hardware is present, and does not delay D1. Evidence: `docs/ROADMAP.md`, `docs/SYNRIA_UPSTREAM_TODO.md`, strategy note section 27.
- 2026-09-17 — Ground truth for object success on the real arm is the operator label plus a final-state still, because the board has no joint feedback or object sensor. Evidence: strategy note section 19.
- 2026-09-18 — **Reversal:** the M3-first D1 decision above is withdrawn. D1 through D5 exclusively target the physical Synria/Alicia-D arm; Yahboom/M3 artifacts cannot satisfy or advance a stage. Reason: operator clarified the flagship embodiment. Evidence: corrected `docs/work-order-ludo-flagship-2026-09-17.md`.
- 2026-09-18 — Recovered physical Synria serial/state/MoveIt bring-up and real-to-sim mirroring are classified **implemented, unmeasured** until their external, uncommitted work is formalized with reproducible commands and committed evidence in this repository. GraspGlue is classified as kinematic attach/release and cannot establish a physical grasp, contact-rich manipulation, or autonomous policy success. No D1 dataset or physical autonomous pick is claimed. Evidence: operator correction and corrected work order; no qualifying artifact is currently committed.
- 2026-09-18 — **Correction:** the ground-truth decision above is insufficiently scoped because it relied on M3 strategy notes. For Synria D1/D2, success requires an independent physical-board observation: an operator label plus a timestamp-linked final-state still from a verified physical camera unless a better independent sensor is added. Joint state and GraspGlue state are not object-success ground truth. Evidence: corrected work order.
- 2026-09-18 — Phase 0 is split into a read-only recovery/safety artifact followed by operator-authorized reduced-speed motion evidence. Controlled stop/hold is the default exit/fault behavior; torque-off is allowed only in a verified support-safe pose or when the manufacturer/controller emergency procedure requires it. Evidence: `reports/synria/recovered_real_arm_state_2026-09-17.md` and corrected work order.
- 2026-09-18 — No seven-to-eight physical recording mapping is assumed. The physical dataset state/action contract must be versioned from observed interfaces; a passive second-finger derivation is allowed only when model-required and physically validated. Evidence: corrected work order and `docs/SYNRIA_UPSTREAM_TODO.md`.
- 2026-09-18 — D2 requires >=14/20 operator-confirmed, camera-backed successes under a pre-registered protocol; D3 requires one SUCCESSFUL physical turn; D4 requires three consecutive SUCCESSFUL physical-roll turns; D5 requires a successful full game. Negative results remain ledgered but do not advance stages. Evidence: corrected work order and `docs/ludo_flagship/MILESTONES.md`.
- 2026-09-18 — **Evidence supplement:** the recovered Synria serial/state/MoveIt and real-to-sim classification is grounded in `reports/synria/recovered_real_arm_state_2026-09-17.md`. That report treats checkout identity, symlink and dirty-tree inventory, inspected code paths, bag metadata, saved scene state, and the audit-time absence of devices/processes as inspected facts. Prior connection, self-check, live mirroring and simulated carry descriptions remain operator/history-reported runtime claims and are not reclassified as measured results. This supplements, and does not rewrite, the earlier recovery-classification decision.
- 2026-09-18 — The D2 threshold of >=14/20 is a pre-registered intermediate integration gate: it requires repeatable majority physical-object performance before exposing the learned policy to Ludo-turn integration, but it is not a claim of final or production reliability. The operator may change the threshold only prospectively, through a recorded decision made before the affected evaluation begins; results already collected cannot be re-gated retrospectively. Evidence: corrected work order and `docs/ludo_flagship/MILESTONES.md`.
- 2026-09-25 — Every physical Synria LeRobot seed dataset must pass a recorded `i4h-lerobot-viz` sanity review before GR00T-Mimic amplification or fine-tuning. Invalid episodes remain recorded with rejection reasons and are excluded from training. Isaac ROS 5.0 remains a post-D1/D2 isolated Thor evaluation, not a migration of the current Humble/Jazzy robot-control path. Evidence: `docs/SYNRIA_GR00T_FINETUNE.md`, `docs/STACK_WATCHLIST.md`, and `docs/notes/isaac_ros_5_0_review_2026-09-25.md`.
- 2026-10-08 — D1 uses the existing Alicia-D leader/follower teleoperation unchanged. Recording observes the follower, reads leader state as the primary action source, and adds no software between the two arms. `next_state` is a separately declared alternative action source and cannot be mixed into the same dataset. Evidence: `docs/ludo_flagship/D1_DATASET_PROTOCOL.md` and `synria_lerobot/physical_contract.py`.
- 2026-10-08 — D1 records the C10 wrist view plus one fixed USB webcam. Operator success requires the task criteria and a timestamp-linked final front-camera still. Quality-valid failed demonstrations remain labeled and count after limits are operator-verified; smoke episodes never count. Evidence: `docs/ludo_flagship/D1_DATASET_PROTOCOL.md` and `synria_lerobot/quality_gates.py`.
- 2026-10-08 — **Correction:** default D1 actions are `next_state`, superseding the primary-leader-action decision above. The operator confirmed that the leader drives the follower through a hardware sync cable, is not connected to the PC, and only follower `/joint_states` is visible. The operator also supplied the vendor interface convention: the recorder uses the follower state one frame later as action, with configurable delay and a default of one. This is a derived action, not an independently observed command. Direct leader-state actions remain an explicit option when the leader is additionally connected by USB, using an isolated read-only instance and a separate dataset. Existing teleoperation stays unchanged. These are operator/documentation interface facts, not current runtime measurements; no vendor code or assets were reused. Evidence: operator setup clarification, `docs/ludo_flagship/D1_DATASET_PROTOCOL.md`, `docs/ludo_flagship/D1_OPERATOR_RUNBOOK.md`, and `synria_lerobot/recorder.py`.
