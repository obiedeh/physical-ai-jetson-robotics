## RESOLUTION (2026-07-25)

Training now reaches PPO iterations (verified: 5/5 iterations, 16 envs,
`training_results.json` written, clean exit). The "deadlock" was **three stacked
problems**, none of them an Isaac Lab install bug:

1. **`rsl-rl-lib` version drift.** The venv had rsl-rl-lib **5.4.0**; Isaac Lab
   2.3.2 pins **3.1.2** (`isaaclab_rl/setup.py`). Even stock Isaac-Cartpole-v0
   crashed with `KeyError: 'actor'`. Fixed:
   `pip install "rsl-rl-lib==3.1.2"` — and re-install
   `torch==2.10.0 --index-url .../whl/cu128` afterwards, because the downgrade
   silently replaces torch with a cu126 build that cannot drive the RTX 5090
   (Blackwell needs cu128).
2. **The actual crash: a `TypeError` in our own script.**
   `runner_cfg.experiment_name` was dataclass `MISSING`: the Synria runner-cfg
   subclasses in `isaac/isaaclab_tasks/synria_pickplace/train_cfg.py` were not
   decorated with `@configclass`, so the parent dataclass `__init__` stamped
   parent defaults (incl. `MISSING`) as instance attributes, shadowing the
   subclass overrides. Fixed: gated `@configclass` decorators + the
   `obs_groups` field required by rsl-rl 3.x.
3. **Teardown pathologies masked the exception.** `app.close()` closes the
   stage, which fires timeline STOP; the stock SimulationContext handler then
   busy-loops forever (the "deadlock"), or with `fastShutdown=True` Kit kills
   the process with exit 0 before the traceback prints (the "false complete").
   Diagnosis requires the no-op STOP-handler monkeypatch (kept, comment
   updated) **plus** `--kit_args="--/app/fastShutdown=False"`.

The env config was never broken — `gym.make` and `RslRlVecEnvWrapper` construct
cleanly. Of the three WIP experimental edits, all are kept: AppLauncher boot
(supported path), STOP-handler no-op (required for clean shutdown), ground-plane
swap (works; revisit only if the real tabletop is needed in training).

**Lesson:** `exit 0` from an Isaac Sim run proves nothing. Require iteration
markers (`Learning iteration`/`Mean reward`) — as
`scripts/linux_rtx/diagnose_isaaclab_baseline.sh` now does.

## The training blocker (NOT fixed)

### Symptom
`bash scripts/run_synria_stack.sh train chess` (or the smoke form
`TRAIN_NUM_ENVS=16 TRAIN_ITERS=3 bash scripts/linux_rtx/train_isaaclab_synria.sh`)
**never reaches a single PPO iteration**. The env builds fully (articulation,
actuators with our gains, action terms all resolve — see
`/tmp/isaaclab/logs/isaaclab_*.log`), then at `sim.reset()` ("Starting the
simulation. Please wait...") the run either:
- **hangs forever** at 100% CPU / 0% GPU (original behaviour), or
- **exits 0** printing a misleading `Training complete` with no iterations and no
  artifacts (after the experimental edits below).

### Root cause (confirmed via gdb on the live process)
1. The script booted via a raw `SimulationApp`. `SimulationApp.__init__`
   **unconditionally sets** `builtins.ISAAC_LAUNCHED_FROM_TERMINAL = False`
   (`isaacsim/.../simulation_app/simulation_app.py:226`). **AppLauncher also
   creates a SimulationApp internally, so it resets the flag to False too** — i.e.
   AppLauncher does NOT fix this.
2. With the flag False, `SimulationContext` registers an interactive timeline-STOP
   handler `_app_control_on_stop_handle_fn`
   (`IsaacLab/source/isaaclab/isaaclab/sim/simulation_context.py:248` registers,
   `:1010` defines). Its body is:
   ```python
   if not self._disable_app_control_on_stop_handle:
       while not omni.timeline.get_timeline_interface().is_playing():
           self.render()
   ```
3. During env construction a stage is **closed** (`omni::usd::UsdContext::
   closeStage()`, seen in the gdb native stack), which fires a timeline **STOP**
   event **outside** the guarded window in `SimulationContext.reset()`
   (`reset()` sets `_disable_app_control_on_stop_handle=True` only around its own
   `super().reset()`, lines 513/531). So the handler runs unguarded and
   **busy-loops forever** because the timeline never goes back to "playing".

### Why this is deeper than the handler
Neutralizing the handler (no-op) or forcing the flag True both **remove the
deadlock but reveal the real problem**: the timeline **stops during `sim.reset()`
and `play()` never sticks** (`is_playing()` stays False). The busy-loop was
Isaac Lab's way of keeping the app alive through a stop; without it the app tears
down (and `--/app/fastShutdown=True` makes that a clean `exit 0`, hiding any
underlying error).

IMPORTANT: setting `ISAAC_LAUNCHED_FROM_TERMINAL = True` is the WRONG fix —
`ManagerBasedEnv` only calls `sim.reset()` (which activates physics handles)
`if ISAAC_LAUNCHED_FROM_TERMINAL is False` (`manager_based_env.py:167`). True →
physics never activates.

### Tests run (all reproduce the failure at `sim.reset()`)
| Variant | Result |
|---|---|
| raw SimulationApp (original) | deadlock (spin forever) |
| `ISAAC_LAUNCHED_FROM_TERMINAL=True` | early shutdown, false "complete" |
| AppLauncher boot | deadlock again (flag forced False) |
| monkeypatch handler → no-op | false "complete" (no iterations) |
| + ground plane instead of `del tabletop` | false "complete" — NOT the ground |
| `num_envs=1` (no cloning) | false "complete" — NOT a cloning issue |

So the failure is **independent of** env count, cloning, and ground plane. It is
fundamental to the `sim.reset()` / timeline-play lifecycle on this install.

### Strong contrast / clue
The **viewer works** with this exact arm (`isaacsim.core` `SimulationContext` +
`SingleArticulation`, 1 env, direct `play()`/`step()`, drives holding torque).
Only the **Isaac Lab `ManagerBasedRLEnv.reset()` path** fails. Prior sessions also
logged recurring Isaac Sim hangs on this machine → smells like an Isaac Lab vs
Isaac Sim 5.1 version/install issue rather than our task config.
